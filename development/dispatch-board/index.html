The job of the board

A delivery night comes down to three questions: what's waiting, who has it, and when will it get there. The board answers all three on one screen, and most changes take one drag.

  • An Unassigned column, then one lane per driver with their car, where they are, and their stops in order.
  • Every card shows the order number, customer, town, total and payment, the delivery window, and an ETA.
  • Problems sit on the card itself: payment not confirmed, a manifest the state system rejected, an ETA that has drifted from what the customer was texted.

Drag and drop that feels physical

The board uses the native HTML5 Drag and Drop API, but the browser's default drag image is a faint, half-transparent ghost. I replaced it: when a drag starts, the card is cloned into an overlay marked inert and aria-hidden that follows the pointer, while the original stays in place, faded, so you can see where it came from.

Positioning runs through requestAnimationFrame, so a burst of dragover events still moves the card once per frame:

/** The browser's own drag image is a faint copy of the small handle; ours is the whole card. */
function hideNativeDragImage(dataTransfer: DataTransfer | null) {
  if (!dataTransfer || typeof dataTransfer.setDragImage !== "function") return;
  const blank = document.createElement("div");
  blank.style.cssText = "position:fixed;top:0;left:0;width:1px;height:1px;pointer-events:none;";
  document.body.appendChild(blank);
  dataTransfer.setDragImage(blank, 0, 0);
  setTimeout(() => blank.remove(), 0);
}

const onDragOver = (dragEvent: DragEvent) => {
  const active = activeRef.current;
  if (!active || active.phase !== "dragging") return;
  // Some browsers end a drag with a 0,0 dragover.
  if (dragEvent.clientX === 0 && dragEvent.clientY === 0) return;
  active.pointer = { x: dragEvent.clientX, y: dragEvent.clientY };
  if (active.frame !== null) return;
  active.frame = requestAnimationFrame(() => {
    active.frame = null;
    place(active.overlay, active.pointer.x - active.offset.x, active.pointer.y - active.offset.y);
  });
};
  • After a drop, the copy waits where it was dropped until the server confirms the move and the board re-renders, then glides into its new slot in 200 ms. A move that fails, or a drag that's cancelled, glides back. If the server hasn't answered in five seconds, it settles anyway.
  • Holding a card near the edge of the board scrolls it, one bounded step per dragover, so it never runs away from you.
  • Firefox only starts a drag that carries data, so every drag sets its own application/x-dispatch-order payload.
  • With prefers-reduced-motion, cards jump to their place instead of gliding.

Secondary actions stay out of the way

Cards would be unreadable if every action had a button. Assigning and moving orders without dragging lives in a ⋯ menu on each card and lane, which also makes the board usable on a touch screen. Everything else about an order, including texting the customer an updated ETA, opens in a panel over the board, so a dispatcher never loses their place.

Live on every screen

Each open board subscribes to a Server-Sent Events stream of order updates and reconciles them with what's on screen, so two dispatchers can work the same night without overwriting each other; an end-to-end test drives two sessions at once to check it. The same data drives a wallboard sized for the TV in a dispatch room and a phone layout for managers away from the desk.

Testing

The board has its own integration and end-to-end suites (board data, order detail, move commands, ETA facts) alongside the app's Vitest unit tests. Shared components are checked in Playwright with axe-core against WCAG 2.2 AA, plus keyboard and visual-catalog tests.
